스펙 주도 AI 코딩, 실무 프레임워크 구축 가이드

MF
metaflyer 팀
2026.07.01 · 읽는 시간 8분

기업에서 도구 도입에서 벗어나, 마이크로(.md) 파일 규칙으로 완전한 AI 협업 환경을 구축하는 법을 3부작으로 소개합니다. 이번 편은 3부작 전체의 마지막 편입니다.

지난 1~2년 사이 AI 코딩 시대가 빠르게 열리면서, '시스템 백엔드를 설계하고 채팅을 완료하는' 모델은 오래된 이야기가 되었습니다. 최근 대부분의 팀의 작업 방식은 Spec(명세) → Plan(설계) → Tasks(작업 분화) → Implement(구현)로 이어지는 흐름으로 정착하고 있습니다.

GitHub Spec Kit이 Spec → Plan → Tasks → Implement의 정석적인 흐름을 제시했다면, Kiro는 같은 흐름에 프로젝트 컨텍스트를 더 깊이 반영한 에이전트 협업 방식을 제안했습니다. 이 둘을 관통하는 공통 결론은 하나입니다. AI에게 좋은 산출물을 얻으려면, 결국 명확하고 지속 가능한 문서 규칙이 먼저 있어야 한다는 것입니다.

이 시리즈는 특정 도구가 아니라, 모든 방법론의 뿌리가 되는 마크다운(.md) 파일 규칙 그 자체와, 그것이 어떤 큰 그림 안에서 팀의 실무 프레임워크로 확장되는지를 정리합니다.

1. 작업 공간의 통합: API와 UI를 하나의 컨텍스트로 묶기

AI 에이전트에게 작업을 위임할 때 흔히 발생하는 문제는 하나입니다. 백엔드 API 스택과 프론트엔드 화면 컨텍스트가 흩어져 있으면, 에이전트가 같은 계약(Contract)을 두 번 다르게 추론합니다.

이를 방지하기 위해 저희 팀은 하나의 프로젝트 워크스페이스 안에 백엔드와 프론트엔드, 인프라를 함께 두고 관리하는 방식으로 정리합니다.

workspace/
├─ backend-api/     # 백엔드 API 서버
├─ frontend-admin/  # 관리자 웹 콘솔
└─ mobile-app/      # 모바일 앱

이 구조의 장점은 AI가 한 작업 공간 안에서 관련 컨텍스트를 함께 참고하고 채팅할 수 있다는 것입니다. 프론트엔드에서 새로운 응답 값이 필요하면, 프론트 코드를 고치는 대신 API 스펙 문서를 먼저 열어 백엔드 팀의 (Full-stack) 인지에서 함께 반영할 수 있는지 검토하도록 규칙을 정합니다. 담당 에이전트는 관련 파일을 임의로 고치는 대신, 문서 협의를 통해 승인된 계약을 근거로만 CLAUDE.md 같은 컨텍스트 파일에 변경 근거를 남깁니다.

2. 3층 자원 문서: 컨텍스트 관리의 명시적 공개

프로젝트마다 모든 컨텍스트를 살계 문서 하나(README.md) 시스템 프롬프트에 몰아넣는 실수를 흔히 봅니다. 문서가 늘어날수록 모든 항목을 늘어놓기보다, 저희는 세 층으로 나눠 관리하는 방식을 권합니다.

[1층] 프로젝트 지식 (CLAUDE.md / AGENTS.md)

작업 공간 최상위에 위치하는 '지도(Map)'입니다. 저장소 전체 관례와 '수용 가능한 접근법' 같은 상위 규칙만 남깁니다.

[2층] 저장소별 지식 (backend/CLAUDE.md 등)

각 저장소가 실제로 채택하고 있는 스타일과 아키텍처를, 배포 설정 관련 근거 문서(예: notification.md)를 통해 정리합니다.

[3층] 세부 규칙 (docs/*.md)

특정 기능이나 도메인에만 적용되는 세부 규칙입니다.

이러한 '점진적 공개(Progressive Disclosure)' 구조를 취하면, 최신 특정 기능을 작업할 때 아주 세밀한 부분까지 매번 다시 문맥을 넣지 않아도 됩니다. 특히 새 규칙 문제가 생기면 스키마(JSON) 형태로 근거 데이터(featureData.json)에 반영한 정책 문서로, AI가 반복하지 않을 판단을 근거로 이어지는 시스템으로 이후 시나리오와 마천되도록 정보를 축적할 수 있습니다.

3. 스펙 문서화 체계: *.plan.md, *.spec.md, *.guide.md

기능 개발을 시작할 때의 흐름도 문서로 미리 정해두는 편이 좋습니다. 기능을 새로 시작하는데 담당자는 무엇을 작성해야 하는지 고민하지 않고, *.plan.md, *.spec.md, *.guide.md 셋만 채우면 되도록 규칙을 만들었습니다. 문서 이름은 요구사항(requirements)-설계(design)-작업(tasks)로 흩어놓지 않고, plan/spec/guide로 통일해도 충분합니다.

1. *.plan.md (기능 및 요구사항)

해당 기능이 왜, 도메인 관점의 목적이 무엇인지 다룹니다. 그리고 그 위의 수용 요구사항을 남깁니다. 검증 가능한 완료 조건(Acceptance Criteria)을 이 문서에서 명확히 밝힙니다.

2. *.spec.md (설계 및 API 명세)

아키텍처 흐름, 데이터 모델, 그리고 구체적인 API 스키마 등을 포함합니다. 테스트 케이스를 문서 안에서 함께 정의하는 것도 좋습니다(예: Lint 설정 등 예상하는 검증 방식까지 포함하는 것도 좋습니다).

3. *.guide.md (운영 가이드 및 안전화)

기능 구현이 완료된 후, 실제 사내에서 어떻게 동작하고 있는지(As-built)를 기록하는 문서입니다.

이러한 문서 분리의 핵심은 AI 스스로 매 단계 입력 범위를 좁혀서 인지부하를 줄이고, 검증 단계를 건너뛰지 않도록 유도한다는 데 있습니다.

4. 교차 AI 검증: Full-Closed 검증

AI가 생성한 코드를 곧바로 배포하는 팀은 언젠가 시스템 안정성에 큰 문제를 겪습니다. 저희 팀에서는 작업하는 에이전트와 검증하는 에이전트의 역할을 분리해서 운영합니다.

작업자 리뷰어 분리 (2가지 권장)

도움을 작성한 AI(예: Claude)가 스스로를 리뷰할 근거는 부족하다는 전제로, 작성 스타일이 다른 검증 에이전트(예: Codex)를 별도로 두어 작업 완료 후 항상 저검토 반드록 함으로써서 두 관점이 교차되도록 만듭니다.

읽기 전용(Read-Only) 제한

리뷰를 맡은 AI 에이전트에게는 코드 수정 권한이 없이 오직 리뷰 결과만 남기도록 하며, 오직 리뷰 관점만 유지하도록 구조로 강제합니다.

구조화된 출력과 Full-Closed 로직

리뷰 결과는 자유로운 텍스트가 아니라 JSON 스키마 형태로 산출하도록 규칙을 정하고, 여기 리뷰 통과 여부에 따라 다음 단계로 진행할 수 있도록 만듭니다. 이러한 Full-Closed 검증 구조를 통해 리뷰 과정이 형식적으로만 남지 않도록 합니다.

5. 문서 지속 업데이트: 문서와 코드의 지속적 동기화

모든 속도가 빨라지면 실제로 남긴 코드와 그 근거가 된 문서가 서로 벌어지기 쉽습니다. 이를 방지하기 위해 두 방향으로 규칙을 정했습니다.

  1. 기능 개발 시 *.plan.md와 *.spec.md를 기반으로 구현을 진행합니다.
  2. 코드가 변경되고 나면, 작업 데이터 반영 여부를 검토해 관련 문서(*.guide.md 등)에 실제 동작한 결과를 다시 기록합니다.

이렇게 세 가지 문서 유형이 반복 순환하며 돌면, 실제 코드와 *.spec.md 처럼 문서가 항상 근거로서 진실 공급원(SSOT) 역할을 계속 유지하게 되고, 이 반영 흐름이 곧 팀의 지속 가능한 AI 협업 환경이 되는 것입니다.

마치며: 유연하고 지속 가능한 AI 협업 환경

지금까지 살펴본 프레임워크는 일부 규칙이 팀마다 만들어져 있겠지만, 여기 아이디어들을 골라 필요한 부분만 참고하셔도 좋습니다. 문서만 잘 정리되어도 AI 협업의 완성도는 크게 달라집니다.

저희 metaflyer 팀도 이 원칙들을 캠페인 빌더와 AI 인사이트 루프 전반에 적용하며 계속 다듬어가고 있습니다. 궁금한 점이 있다면 언제든 편하게 문의해주세요.
