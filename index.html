픽업 가능을 필터로

"픽업 가능"을 정렬 옆 토글로 두어, 지금 받을 수 있는 상품만 남기는 게 한 번의 탭으로 끝납니다.

품절 대신 재입고 예정

재고 없는 상품을 지우지 않고 "재입고 예정" 라벨을 붙여, 대체 상품을 찾거나 기다릴지 보호자가 고를 수 있게 했습니다.

금액은 확정 직전에 한 번

할인 반영 후 최종 결제 예정 금액을 예약 확정 버튼 바로 위에 두어, 결제 전 마지막 확인이 한 블록에서 끝나게 했습니다.

네 흐름이 공유하는 규칙

Rule 01

CTA는 화면당 하나

예약하기 · 진료 예약하기 · 예약 확정하기처럼 화면마다 Primary는 하단 버튼 하나만 둡니다.

Rule 02

색은 역할로 나눈다

블루는 행동(버튼 · 활성 탭), 핑크는 시점 알림에만 씁니다. 같은 색이 두 가지 의미를 갖지 않습니다.

Rule 03

반려동물이 항상 문맥

예약 · 접종 · 기록 화면 상단에 대상 반려동물을 고정해, 누구의 정보인지 다시 묻지 않게 했습니다.

UX에서 고려한 것

화면 규칙 아래에는 보호자의 상황에 대한 가정이 있습니다. 페르소나 인터뷰에서 반복된 감정(죄책감 · 초조함 · 막막함)을 줄이는 쪽으로 판단 기준을 정했습니다.

UX 01

불안한 순간을 먼저 설계

보호자가 앱을 여는 순간은 대부분 불안할 때입니다. 응급 · 재고 없음 · 예약 실패 화면을 정상 화면보다 먼저 그리고, 다음 행동 버튼을 항상 남겼습니다.

UX 02

확정과 예측을 구분

병원이 확정한 정보와 앱이 계산한 예측을 같은 모양으로 보여주지 않았습니다. 예측은 점선 테두리와 '예정' 라벨로 구분해 신뢰를 잃지 않게 했습니다.

UX 03

한 손 · 한 번의 탭

산책 중이거나 아이를 안고 있는 상황을 가정해 주요 액션을 화면 하단 엄지 영역에 두고, 예약까지의 탭 수를 세 번 이내로 제한했습니다.

UX 04

반려동물 한 마리 기준

다견 가정에서도 화면이 섞이지 않도록 모든 정보의 기준을 '선택한 아이'로 고정하고, 전환은 상단 프로필 하나로만 하도록 했습니다.

UX 05

전화를 지우지 않기

모든 사람이 앱을 믿지는 않습니다. 실시간 정보 옆에 전화 버튼을 남겨, 앱이 전화를 대체하기보다 전화 전 확인 단계를 대신하도록 했습니다.

UX 06

시각을 함께 표시

재고와 진료 가능 여부처럼 변하는 정보에는 항상 'n분 전 확인'을 붙였습니다. 언제 기준의 정보인지 알면 보호자가 직접 판단할 수 있습니다.

아홉 개가 이어져 있다는 말은 글보다 화면이 증명해야 합니다. 브랜드 사이트의 역할에 맞춰 정보 밀도를 낮추고, 스크롤 자체가 여정을 따라 이동하는 경험이 되도록 레이아웃과 인터랙션을 설계했습니다.

하나의 Pain Point → Solution 서비스를 소개하는 모든 블록을 '제목 · 설명 · 핵심 기능 3줄 · 이미지'라는 같은 틀로 만들고, 이미지 위치만 좌우로 번갈아 놓았습니다.

기획부터 개발, 배포까지 혼자 진행한 프로젝트입니다. 단계마다 무엇이 바뀌었는지 순서대로 돌아봤습니다.

01

기획

노션에 시장 선정부터 페르소나, JTBD, Pain Point 매트릭스까지 문서로 쌓았습니다. 숫자를 먼저 모은 덕분에 "왜 이 기능이 필요한가"에 답할 근거가 생겼고, 이후 기능을 덜어낼 때도 기준이 흔들리지 않았습니다.

02

디자인

Figma에서 Critical Pain Point 세 개에 해당하는 흐름부터 그렸습니다. 처음엔 기능별로 탭을 나눴지만, 보호자는 기능이 아니라 '우리 아이' 단위로 생각한다는 걸 인터뷰에서 확인하고 반려동물 한 마리 기준으로 구조를 다시 짰습니다.

03

개발

Cursor와 Claude로 직접 화면을 구현했습니다. 디자인에서는 자연스러웠던 상태 표시가 실제 데이터를 넣으니 너무 많아졌고, 그때 '상태는 한 곳에서만 말한다'는 규칙을 만들었습니다. 코드로 옮기면서 규칙이 구체적인 숫자와 조건으로 바뀌었습니다.

04

배포 · 검증

배포한 뒤 실제 기기에서 써 보며 가장 많이 고친 건 예외 상태였습니다. 재고가 없거나 진료가 끝났을 때 화면이 비어 버리면 사용자는 바로 전화를 겁니다. 빈 화면마다 다음 행동을 넣는 작업이 마지막까지 이어졌습니다.

회고

이 프로젝트에서 붙잡고 싶었던 건 화면의 완성도가 아니라 보호자가 실제로 겪는 불편이었습니다. 병원이 지금 열었는지 몰라 전화를 걸고, 병원을 옮길 때마다 진료 기록을 처음부터 다시 설명하고, 처방식 재고를 몰라 헛걸음하는 순간들. 화면 하나하나를 그 불편을 하나씩 덜어내는 장치로 설계하려 했습니다.

디자이너로서 개발까지 직접 맡으면서 우여곡절도 많았습니다. 설계에서는 당연했던 흐름이 구현 단계에서 막히기도 했고, 예외 상황을 하나씩 조건으로 풀어내느라 같은 화면을 몇 번씩 다시 만들었습니다. 그렇게 끝까지 붙잡고 실제로 동작하는 서비스를 배포했을 때, 설계한 의도가 사용자의 손에 그대로 닿는다는 성취감을 처음으로 온전히 느꼈습니다.

다음 단계에서는 설계 단계에서 세운 목표 수치(예약 30초, 노쇼 −15%)를 실제 사용 데이터로 검증하고, 병원 측 화면까지 확장해 보호자와 병원 양쪽의 부담을 함께 줄이는 구조를 만들고 싶습니다. 커넥트펫은 제게 디자인이 화면에서 끝나는 일이 아니라, 사용자의 불편이 실제로 줄어드는 순간까지 책임지는 일이라는 걸 알려준 프로젝트입니다.
